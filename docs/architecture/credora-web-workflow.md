The browser opens the Next.js 16 application in `apps/web`. React 19 renders the issuer, organization, superadmin, holder and public verification screens. TypeScript supplies the application types; Tailwind CSS 4 and app-local shadcn/Radix components provide styling and controls. QR libraries generate share codes, while ZXing reads codes through the camera. Issuers and administrators connect an injected Ethereum wallet; public verifiers do not need to sign in.

1. **Authenticate the issuer.** The web app requests a nonce-based challenge from `POST /auth/challenge`. The wallet signs the message through `personal_sign`, then the app sends the signature to `POST /auth/verify`. The Node.js API verifies it and returns an expiring session. The private key stays inside the wallet; the API receives a signature.
2. **Prepare the credential.** The API checks the issuer's organization access and registry authorization, creates an issuance draft and saves operational state in SQLite. An organization can require internal review of the prepared payload. An approved organization is activated by a superadmin transaction; its administrators then manage authorized issuer wallets on-chain. That activation is a setup prerequisite, rather than a platform approval for every credential. Internal review is an API workflow policy, not an on-chain multisignature rule.
3. **Publish the manifest and compute the hash.** `POST /issuances/{id}/metadata` writes the public JSON manifest through the storage adapter, optionally referencing a separately uploaded image. IPFS returns a content identifier and `ipfs://` URI. The shared `credential-core` package computes Keccak-256 over the versioned, ABI-encoded credential fields, including that URI. Organization credentials use the v3 payload with organization binding; legacy credentials retain v1 rules. The CID locates metadata bytes; the credential hash binds the proof. They are different identifiers.
4. **Sign and issue.** The web app uses viem and the browser wallet to call the Solidity registry through an EVM RPC endpoint. The organization registry checks that the organization is active and the signer is authorized before recording the immutable credential. Legacy v1 issuance uses its separate registry. The API cannot confer on-chain authority through a database role.
5. **Confirm and display.** The web app sends the transaction hash to `POST /issuances/{id}/confirm`. The API checks the receipt, transaction payload and registry record against the draft before marking the SQLite row confirmed. Timed event reconciliation updates chain-derived projections from registry history. The holder's wallet view uses these projections to list credentials and prepare links or QR codes.
6. **Verify independently of database claims.** A verifier opens a credential hash, verification URL or share QR. An expiring share first resolves its fixed selection of public hashes. For each hash, the API reads the organization registry and, if absent there, the legacy registry, retrieves the manifest and recomputes the appropriate hash. It compares the hash and bound fields such as issuer and learner before returning a result. SQLite rows alone cannot establish validity.

The API is one Node.js HTTP process written in TypeScript, using `node:http`, rather than a collection of separately deployed services. viem performs RPC reads, ABI interactions and signature-related operations. SQLite, accessed through `node:sqlite`, stores sessions, organization workflow data, drafts, audit records, share capabilities and chain-derived projections. Only the chain-derived portion is rebuildable from ledger history; organization applications and other off-chain operational data need backups.

Solidity and OpenZeppelin implement registry authority and access control. Foundry builds and tests the contracts; Anvil supplies the local development chain. These are development tools, rather than browser or API runtime components. The configured deployment uses Docker Compose to run the Next.js web process, API, Caddy HTTPS reverse proxy and scheduled SQLite backups. EVM RPC and IPFS upload/gateway endpoints are configured dependencies. This diagram describes repository code and deployment configuration; it does not establish that a particular production deployment is running.

Public verification distinguishes malformed references, missing credentials, metadata mismatch, ledger unavailability and metadata unavailability. On an API network error or HTTP 503, the shared web verification helper attempts direct RPC and public IPFS gateway verification. **That implemented fallback currently targets the legacy v1 registry and metadata; it does not verify organization v3 credentials.** A standalone verifier can implement the v3 ABI and canonical hash rules, but the current web fallback has that narrower scope. If IPFS is not configured, the API selects a local file adapter with `local://` URIs; those files cannot be fetched through the public IPFS fallback.

Issued proofs remain immutable. Organization suspension blocks future issuance and is shown separately from the validity of previously issued proofs. A share's expiry or revocation stops future bundle lookup; it does not erase public credential records or prove that the presenter controls the learner wallet. Package-level v2 selective-disclosure helpers exist, but the shown HTTP verification route handles v1 and v3, so this diagram does not imply a deployed v2 verification flow.
