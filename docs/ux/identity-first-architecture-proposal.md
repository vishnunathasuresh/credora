# Account-first identity architecture proposal

Status: proposed, 2026-10-29. This is an implementation contract for review, not an accepted ADR or a claim that these features exist. The [product direction](../roadmap/product-direction.md) requires numbered decisions for authentication/recovery, wallet association, and profile privacy before implementation. Amend [ADR 0011](../decisions/0011-profile-identity-and-publication.md) explicitly when those decisions are accepted.

## Current boundary

`apps/api/src/migrations.ts` stores `profiles.wallet_address` as required and unique, and `profile_credentials` as ordered selections. `apps/api/src/index.ts` looks up and authorizes profiles using the wallet session address and filters displayed selections and credential decoration against that address. `packages/auth` creates a wallet-signature challenge; `/auth/verify` creates an address/roles bearer session, and `apps/web/src/lib/wallet-session.ts` saves its token in sessionStorage. The challenge text labels the expiry as `Issued At` and lacks SIWE's full domain/URI binding; it must not be reused unchanged for account linking. Roles and organization and issuance routes are extensively address-scoped. A new account session must never satisfy those checks as if it were a wallet session.

ADR 0011 calls the current wallet owner model transitional, and makes profile content, handle and publication authoritative application data. Chain and content-addressed metadata remain authoritative for proof; confirmed API issuance rows are projections. Neither a profile name nor an account association changes a credential's immutable learner address. Profile selection is a display choice, not independent proof verification or proof of present wallet control.

## Selected authentication architecture

Use **Sign in with Google through Supabase Auth** as the primary account login, per the product decision. Supabase manages the Google OAuth exchange and identity; Credora retains its existing API/database as the authority for account IDs, profiles, publication and wallet links. Configure Google credentials and the Supabase callback using the [official Google provider guide](https://supabase.com/docs/guides/auth/social-login/auth-google), exact allowed redirect URLs, and a separate deployment configuration. No Google client secret, Supabase secret/service-role key, wallet private key or refresh token belongs in browser bundles or logs. Only the publishable key is public. Hosted or self-hosted Supabase is an operational choice, not a presumption that a project, credentials or deployment already exists.

**Recommended web flow:** TanStack Start is a same-origin backend-for-frontend (BFF). Initiate Supabase OAuth with PKCE and exchange the one-use callback code server-side, checking state/PKCE and exact redirect; use a request-scoped Supabase client. Store Supabase access and refresh tokens encrypted in a server-side session store keyed by an opaque random `HttpOnly` cookie; serialize refresh/rotation per session, replace tokens atomically and never expose them to browser JavaScript. This is a custom server-only storage integration, not an assertion that the standard SSR helper automatically produces HttpOnly token storage; prove its behavior with the pinned SDK before production. BFF forwards the access token to the standalone Node API over authenticated TLS/internal transport. Browser gets only the opaque session and CSRF token. Handle callback errors and missing/expired sessions without exposing tokens or codes; redirect to a clean URL and prevent caching.

Alternative: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/advanced-guide) stores access and refresh tokens in browser-readable cookies for its standard browser/server session model. This fits documented SDK behavior and is simpler, but exposes refresh tokens to JavaScript and requires careful rotation across concurrent requests. A browser-only SDK generally stores tokens in localStorage. Both increase XSS exposure relative to the server-only BFF. Do not describe the recommended BFF as stock `@supabase/ssr`: its request-scoped token store, refresh races, revocation and failure recovery require implementation and tests. Supabase documents PKCE and the [server package choices including TanStack Start](https://supabase.com/docs/guides/auth/choosing-a-server-package); verify current SDK support and version, rather than promising turnkey integration.

**Standalone API trust boundary:** accept only a Supabase Auth access JWT sent by the BFF, not a Google ID token, an arbitrary request user ID, decoded-unverified claims, a publishable key or an account ID as authentication. Verify cryptographic signature using a maintained verifier or Supabase `getClaims`, configured trusted project issuer and JWKS, an explicit algorithm allowlist matching the configured asymmetric keys, exact expected audience (normally `authenticated`, confirm deployment configuration), `exp`, applicable `nbf`, and nonempty `sub`; require the intended authenticated user token class and reject anonymous/service tokens. Never choose JWKS/issuer from token-controlled URLs, accept `none`, or allow algorithm confusion. Pin URL to configuration and handle unknown `kid`, rotation and cache invalidation safely; fail closed if no trusted key is available. [Supabase JWT documentation](https://supabase.com/docs/guides/auth/jwts) describes JWKS, and [getClaims](https://supabase.com/docs/reference/javascript/auth-getclaims) explains asymmetric verification and symmetric-key network fallback. Recommend asymmetric signing and no JWT shared secret in the API. Explicitly test issuer, audience, algorithm, time and token type even if the selected verifier offers defaults.

A verified JWT `sub`, namespaced by the exact Supabase issuer, maps through a unique `(issuer, subject)` identity row to a random immutable Credora account ID. Create this mapping and the account transactionally and idempotently on first sign-in. Never match or merge by email, Google display name, handle or client-provided ID. A restored Supabase project or provider account with a different subject does not automatically reclaim a Credora account. Avoid persisting Google email or profile details unless a separate user-facing need and policy justify them. Supabase/Google recovery recovers account login only, never wallet possession or chain authority; loss of Google access can make the account inaccessible. No support override or alternate recovery is promised.

`getClaims` verifies the JWT but an unexpired JWT may outlive a revoked Supabase session; use Supabase `getUser` online and check session/account status for sensitive link, unlink and migration operations, revoke the BFF session at logout, and bound ordinary-session exposure with short access-token lifetimes. Fresh authentication for sensitive changes must be provable (for example an explicit new Google reauthentication flow with verified authentication time); if the provider cannot supply reliable freshness, do not claim it exists or silently substitute a refresh. Fail closed until an appropriate step-up is implemented. Key-cache revocation and provider outage are separate operational concerns; follow [Supabase signing-key guidance](https://supabase.com/docs/guides/auth/signing-keys) and provide a cache-busting incident procedure.

## Account and profile contract

- Stable account ID is distinct from handle, Supabase subject, wallet and profile ID. A profile has one account owner; an account has at most one profile. Preserve existing profile IDs. Handle rules, cooldown and old-link behavior remain ADR 0011 until changed through an ADR. Account creation, handle claiming, profile editing and publishing an empty profile never need a wallet; handle uniqueness and updates use database constraints and transactions.
- Profile editing, publication and management require verified account identity and ownership. Profiles start private. Public responses include only explicitly published fields and explicitly selected eligible credentials. Publication explains association with public wallet records and that copies cannot be recalled. Preserve ordering and the existing avatar URL fetch boundary. User-written claims are distinct from issuer-backed evidence.

## Wallet association and authority

Use a separate `wallet_links` record with normalized address, owning account ID, link state and timestamps; enforce one active owner per normalized address globally, while allowing an account multiple linked wallets. The user explicitly selects a wallet when resolving a recipient or acting as issuer. Never accept an address from an account session as proof of wallet possession.

For link, first require a fresh account authentication, then create a server-held, high-entropy one-use challenge bound to account ID, session, exact normalized address, chain ID, action `link wallet`, configured domain/URI, issued-at and expiration. Present a human-readable [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361) message with an explicit link statement; validate the entire server-stored message and binding rather than client-provided claims. Consume the challenge and insert the link atomically; return a conflict if already linked, never automatically merge accounts or reassign an address. Support only EOA signature verification initially; if contract wallets are later supported, use chain-specific ERC-1271 verification, distinguish RPC outage from invalid signature, and specify revalidation. Reject unsupported types clearly.

A link records demonstrated control at link time, not permanent or current control. For sensitive actions, require a fresh purpose-bound wallet signature or an explicitly separate, short-lived wallet-authenticated capability for the selected address, and recheck existing chain/organization authority at the operation. An account session, even recovered, confers no issuer, reviewer, admin, transaction signing or credential transfer authority. Existing wallet shares remain separately authorized and must retain their current access checks. Define link removal and account recovery to revoke wallet capabilities and invalidate in-flight challenges. A wallet can be re-associated with another account only after explicit unlink, fresh proof by its owner, and conflict handling; never infer permission from a new account or handle.

Publication and credential lists must join confirmed projections to an *active linked address matching each immutable learner address*, with explicit selection; a profile's linked wallets must not be published automatically. On unlink, atomically remove or suppress selections for that address and stop decoration; preserve the chain record. Re-linking does not republish those selections without a new explicit selection. Re-authentication after account recovery restores editing of application data only; credentials remain bound to their original learner addresses. Before sensitive wallet-bound actions the old wallet must sign again. For recipient lookup resolve a selected eligible address to a concrete address and bind issuance confirmation to it; a handle change or later link change never redirects a prepared issuance.

## Sessions and browser security

Deploy web and API behind one HTTPS origin (for example `/api` reverse proxy) so production uses a host-only `__Host-` cookie, `Secure`, `HttpOnly`, `Path=/`, `SameSite=Lax`, no Domain. Never put the new session token in browser storage or URLs. Issue at least 256 random bits; store a hash/verifier with account, expiry, authentication time, assurance and revocation state. Rotate on authentication, privilege transitions and recovery; revoke on logout and support all-session revocation. Set explicit idle and absolute expiries; suggested defaults 12 hours idle and 7 days absolute, with fresh authentication within 5 minutes for link, unlink, identity-provider security changes. Do not silently extend the absolute expiry. Sessions are not wallet proof. Avoid logging cookies, session IDs, signatures or authentication tokens; adopt CSP and output encoding as XSS defenses. See [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Use synchronizer CSRF tokens tied to the session, validate them and exact Origin on every unsafe browser request including login and recovery (use a short-lived pre-auth session for these); reject missing or unexpected Origin for browser mutation endpoints, with a separate explicitly designed non-browser interface if needed. No mutations via GET. SameSite is defense in depth, not the only control; see [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Same-origin is the recommended default: disable CORS unless explicitly required. If a separately hosted web origin is later allowed, use an exact configured origin allowlist, `Vary: Origin`, credentialed CORS only for those origins, no wildcard, and retain CSRF and origin validation; ensure cookie site and browser constraints are understood. Do not trust forwarded host or client IP except from explicitly configured reverse proxies.

Apply bounded request bodies and a shared, persistent rate limiter to OAuth initiation and callback, wallet linking and sensitive mutations, keyed by trusted client IP plus appropriate account/challenge identifiers. Include global limits and fair per-account limits so distributed guessing and IP rotation do not bypass controls; avoid permanent attacker-triggerable lockout, return 429 and retry guidance, and avoid account-enumerating recovery responses. A process-local map is insufficient for multiple instances or restarts. Define operational thresholds with measured traffic; fail closed for authentication if the limiter/store is unavailable. Distinguish API, authentication store, rate limiter, RPC and metadata failures in the UI. Log minimal security events without secrets.

## Safe migration and compatibility

1. Back up and verify a restorable consistent SQLite snapshot before migrations; deploy additive account, identity mapping, session and link tables plus nullable account ownership behind a flag. Preserve existing `profiles.id`, content, selections, publication, handles, cooldown and wallet association. Keep legacy wallet authentication working during transition; new account sessions cannot enter legacy role routes.
2. Do **not** create user-accessible accounts from wallet addresses alone. A legacy holder starts a migration from their existing signed wallet session, signs in through Google and explicitly confirms the profile/account association. Bind all steps to the same session and a fresh action-specific wallet signature. In one transaction check that the legacy profile and wallet are unclaimed, create the account and verified link, assign its profile, preserve selections and publication, consume challenge and invalidate legacy profile-management sessions. Abort cleanly on any uniqueness conflict or concurrent claim. A wallet that has no profile can associate to a new account without inventing one.
3. If an existing account tries to link a wallet with a legacy profile, show a conflict and an explicit migration flow requiring both fresh account authentication and fresh wallet proof; never merge profile contents, replace either profile, or release a handle automatically. Two populated profiles need an explicit resolution policy before merge support; until then reject without data loss. If a wallet is already linked to a different account, reject and require that account's authorized unlink flow. Lost legacy wallet keys cannot prove ownership and have no automatic migration or support override.
4. Backfill no privileged capability from a link. Migrate profile read/write queries and decoration joins to account ownership and active links; gate legacy profile mutation once claimed. Other issuer/admin routes continue to require their existing separately authenticated address and authoritative checks until explicitly migrated. Roll out with a measured coexistence window, then retire old wallet-only profile editing and invalidate legacy sessions; never revoke a user's on-chain wallet role by retiring an API session. Test rollback against a copy, and do not restore an old database over newer user writes without a documented reconciliation procedure.

## Implementation sequence and acceptance gates

1. Accept three numbered ADRs; update ADR 0011, architecture overview, glossary, operator backup and privacy documentation. Specify ownership, multi-wallet selection, recovery, migration and old wallet authority explicitly.
2. Prototype pinned Supabase SDK and JWT verification with the current Node/SQLite runtime; prove PKCE callback, exact-origin cookies, server-only token storage, refresh rotation and restart-safe throttling before selecting versions. Define reviewed DB migrations, foreign keys, transactions, and backup/restore procedure. No schema or library fit is presumed.
3. Add account and profile contracts in API/shared packages, then web join, handle, editor and publication flow. Build wallet association and migration behind flags; maintain old issuer/share access until equivalent checks are verified. No package imports app code. Keep direct verifier and protocol unchanged.
4. Exercise registration without wallet, new private profile, publication with zero credentials, handle collision/cooldown, Google sign-in and account recovery. Test OAuth state and PKCE replay, callback errors, invalid issuer/audience/algorithm/expiry, key rotation, revoked sessions, stolen session, CSRF, fixation and throttling. Test session revocation and no credential or privileged authority transfer after recovery. Test link replay, duplicate and concurrent links, unlink visibility, signature mismatch, lost wallet, and RPC failure for any later contract-wallet support.
5. Migrate representative live-schema fixtures including published and private profiles, ordered selections and conflicting accounts. Test transactional interruption, rollback, session cutoff, two-profile conflict and backup restore; verify that restored authoritative profile and identity mapping data survive while chain projections are rebuildable. Run existing profile, wallet-share, backend roles and outage e2e suites and actual browser ceremonies; verify direct third-party proof checking and public privacy. Security review and an operational recovery/incident runbook are launch gates.

## Decisions requiring product/operator input

- Confirm Google/Supabase account recovery dependency and whether a later independent login or recovery option is needed. Confirm hosted versus self-hosted Supabase and operation of Google OAuth credentials.
- Confirm production domain, allowed origins, HTTPS termination, deployment topology, trusted proxies, persistent rate-limiter and backup ownership, retention and restore objectives before launch. These are operational commitments, not assumptions that infrastructure exists.
- Decide whether multiple linked wallets and suppression of previously selected credentials on unlink match the desired product behavior; decide how, if ever, two populated profiles are merged. Confirm whether the current handle reuse/cooldown and existing publication preservation remain acceptable during migration.

Routine implementation choices such as exact library version, table names, expiry defaults and measured rate thresholds can be settled by the implementer within the above invariants, reviewed ADRs and operator constraints. If the above input is unresolved, do not ship the dependent behavior as settled policy.
